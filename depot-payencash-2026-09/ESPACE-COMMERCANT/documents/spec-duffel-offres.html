À quoi sert ce document. Duffel est le fournisseur des vols (et des hôtels) de PayEnCash. Cette spec décrit, pour le développeur, comment créer une offre de A à Z : obtenir la clé, chercher des vols, présenter le prix (tarif Duffel + notre marge), encaisser en espèces, puis réserver. Base : duffel.com/docs (vérifier la version exacte de l'API).

0 · Rôle dans le produit

Duffel renvoie les offres réelles des compagnies (plus de 200 compagnies : NDC + GDS + low-cost) et, via Duffel Stays, des hôtels. C'est la matière première vendue dans l'app PayEnCash. Le client choisit → il paie avec un bon d’achat (Bon d’achat PayEnCash ou Bon d’achat PayEnCash, achetés au comptoir d'un commerce) → AJEK crée la commande (order) chez Duffel → le client reçoit son reçu + code.

1 · Obtenir la clé d'accès (access token)

  1. Dashboard app.duffel.com (connecté).
  2. Bascule le mode : Test = données fictives (compagnies de démo, prix bidon) ; Live = vrais tarifs. ⚠️ Le mode Live doit d'abord être activé (infos société + moyen de paiement).
  3. Settings → Access tokens → Create token → nom + mode → Copy.
  4. La clé (duffel_live_… / duffel_test_…) n'est affichée qu'une fois — la stocker aussitôt.
Sécurité (impératif) : la clé est un secret serveur. Jamais dans l'app client, jamais dans le front, jamais dans un dépôt Git, jamais collée dans un chat. Elle vit dans une variable d'environnement côté back-end (ex. DUFFEL_TOKEN).

2 · Le flux de création d'offre (3 étapes)

1
Recherche — Offer Request
On envoie les trajets voulus ; Duffel renvoie les offres disponibles.
# POST https://api.duffel.com/air/offer_requests
# Headers : Authorization: Bearer $DUFFEL_TOKEN · Duffel-Version: v2 · Content-Type/Accept: application/json
{
  "data": {
    "cabin_class": "economy",
    "passengers": [{ "type": "adult" }],
    "slices": [
      { "origin": "MRS", "destination": "ALG", "departure_date": "2026-08-15" },
      { "origin": "ALG", "destination": "MRS", "departure_date": "2026-08-29" }
    ]
  }
}
2
Résultats — Offers
Chaque offre porte un id, total_amount + total_currency, la compagnie (owner.name) et les segments. On trie par prix.
# Les offres sont dans la réponse (return_offers par défaut), ou : GET /air/offers?offer_request_id=...
data.offers[] → { id, total_amount: "189.90", total_currency: "EUR", owner: { name: "Air Algérie" }, slices[].segments[] }
3
Réservation — Order
Après encaissement des espèces, on crée la commande avec l'offre choisie + les données passager + le paiement à Duffel.
# POST https://api.duffel.com/air/orders
{
  "data": {
    "type": "instant",
    "selected_offers": ["off_123..."],
    "passengers": [{ /* identité, date naissance, contact... */ }],
    "payments": [{ "type": "balance", "amount": "189.90", "currency": "EUR" }]
  }
}
⏱️ Une offre a une durée de validité et le prix peut changer entre la recherche et la réservation → afficher un prix « sous réserve de confirmation » et re-vérifier avant l'order. Duffel propose aussi des hold orders (réserver sans payer immédiatement) selon les compagnies. C'est LE mécanisme de notre « prix bloqué 1 h » : hold order à la confirmation → le client va payer en espèces → règlement déclaré → payment sur l'order → émission (PNR + e-tickets). Si le hold expire sans paiement : l'offre est libérée, la commande passe « annulée — hors délai ».

3 · Marge & prix affiché

Prix payé par le client = tarif Duffel + marge AJEK. La marge est librement fixée par AJEK (≈ 15–30 %) — c'est notre commission d'agence. Les frais Duffel (~3 $/commande + 1 % du montant + 1–2,5 $/segment passager, +2 % si change de devise) sont un coût à déduire. (17/09, révisé le 18/09 au soir) Le coût d'encaissement dépend du moyen : frais du prestataire en ligne pour un Bon d’achat PayEnCash , ou commission du commerçant 1,10 % HT + frais du prestataire qui le prélève (Stripe, 1,5 % + 0,25 €) pour un Bon d’achat PayEnCash — Étape 2 §1b.

Techniquement, la marge s'ajoute côté AJEK au total_amount Duffel avant affichage ; on ne modifie pas l'offre Duffel, on présente total_amount + marge comme prix de vente.

4 · Le paiement (spécificité cash PayEnCash)

Le client paie avec un bon d’achat (Bon d’achat PayEnCash, ou Bon d’achat PayEnCash réglé en ligne par le prestataire). AJEK, elle, règle Duffel pour émettre le billet — typiquement via le solde Duffel Payments (payment.type: "balance") approvisionné par AJEK. Séquence :

  1. Recherche + choix (étapes 2·1 et 2·2).
  2. Règlement — notification du prestataire (en ligne) ou espèces comptées par l'agent → reçu + code (voir reçu client).
  3. Création de l'order (étape 2·3) financée par le solde AJEK.
  4. Rapprochement : transaction du prestataire (en ligne) ou dépôt de l'agent (espèces) ↔ facture Odoo.
Point à border (LCB-FT / trésorerie) : le décalage « règlement client (virement du prestataire à J+n, espèces déposées) » ↔ « paiement à Duffel par AJEK » implique une avance de trésorerie et une traçabilité stricte des espèces. À cadrer avec l'expert-comptable.

5 · Couverture & limites (impact produit)

Plus de 200 compagnies, mais la disponibilité varie selon le contenu (NDC / GDS / LCC).

TypeExemples utilesSur Duffel ?
Maghreb (diaspora)Air Algérie, Transavia✅ oui (Air Algérie confirmée)
Europe régulier / NDCVueling, Transavia, Air France, Lufthansa…✅ oui
Ultra-low-costRyanair, easyJet, Wizz Air⚠️ limité / souvent absent
Conséquence directe sur l'offre « découverte à petit prix » : les billets à ~15–30 € sont surtout du Ryanair / Wizz Air, mal couverts par Duffel. Le script de test (§8) tranchera route par route : si Duffel ne renvoie pas ces tarifs, il faudra soit ajuster les destinations « découverte » à ce que Duffel propose vraiment, soit envisager une 2ᵉ source à terme.

6 · Hébergement — Duffel Stays (le bundle < 100 €)

Duffel propose une API Stays (hôtels) séparée : recherche par ville/dates → tarifs → réservation. Elle permet le bundle « vol + hôtel » chez un seul fournisseur — cœur de l'idée « un week-end découverte à moins de 100 € » (billet cheap + 1–2 nuits).

# Recherche d'hôtels (schéma indicatif — voir duffel.com/docs/api/stays)
# POST https://api.duffel.com/stays/search
{ "data": { "location": {"radius": 10, "geographic_coordinates": {…}}, "check_in_date": "2026-09-18", "check_out_date": "2026-09-20", "rooms": 1, "guests": [{"type":"adult"}] } }

Même logique de marge : prix hôtel Duffel + marge AJEK. On peut composer un « prix pack » = vol + hôtel + marge, affiché comme une offre unique payable en espèces.

8 · Script de test (sortir les vrais tarifs)

À lancer côté serveur / terminal, clé en variable d'environnement (jamais en clair). Nécessite curl + jq.

export DUFFEL_TOKEN="duffel_live_…"   # reste côté serveur
routes="
MRS ALG 2026-08-15 2026-08-29
MRS TUN 2026-08-15 2026-08-29
MRS RAK 2026-08-15 2026-08-29
MRS FCO 2026-09-18 2026-09-21
MRS BCN 2026-09-18 2026-09-21
MRS OTP 2026-09-18 2026-09-21
MRS BUD 2026-09-18 2026-09-21
MRS OPO 2026-09-18 2026-09-21
MRS LIS 2026-09-18 2026-09-21
MRS NAP 2026-09-18 2026-09-21
MRS ATH 2026-09-18 2026-09-21
"
echo "$routes" | while read o d da dr; do
  [ -z "$o" ] && continue
  resp=$(curl -s https://api.duffel.com/air/offer_requests \
    -H "Authorization: Bearer $DUFFEL_TOKEN" -H "Duffel-Version: v2" \
    -H "Content-Type: application/json" -H "Accept: application/json" \
    -d "{\"data\":{\"cabin_class\":\"economy\",\"passengers\":[{\"type\":\"adult\"}],\"slices\":[{\"origin\":\"$o\",\"destination\":\"$d\",\"departure_date\":\"$da\"},{\"origin\":\"$d\",\"destination\":\"$o\",\"departure_date\":\"$dr\"}]}}")
  cheapest=$(echo "$resp" | jq -r '[.data.offers[]? | {c:.owner.name,p:(.total_amount|tonumber),cur:.total_currency}] | sort_by(.p) | .[0] | if .==null then "aucune offre Duffel" else "\(.p) \(.cur) — \(.c)" end')
  printf "%-4s -> %-4s (A/R) : %s\n" "$o" "$d" "$cheapest"
  sleep 1
done

Sortie : une ligne par destination (prix + devise — compagnie, ou « aucune offre Duffel »). Ces chiffres remplacent les fourchettes marché dans l'analyse et le modèle.

9 · Sécurité & bonnes pratiques

  • Clé côté serveur uniquement (variable d'env), jamais front / app client / Git / chat.
  • Mode Live pour de vrais prix ; le Test renvoie des données fictives.
  • Chercher ne réserve ni ne facture ; seule la création d'order engage un paiement.
  • Prix volatil : re-vérifier l'offre avant l'order ; gérer l'expiration.
  • Rate limits Duffel : espacer les requêtes en masse (sleep).
  • Version d'API : fixer Duffel-Version à la version validée (voir dashboard/docs).

Annulations & remboursements — ce que Duffel fait VRAIMENT (vérifié 27/08)

  • Éligibilité : l'annulation par API n'est possible que si l'order porte "cancel" dans available_actions — sinon, demande manuelle via le dashboard Duffel (prévoir ce chemin dans l'orchestrateur : c'est lui qui justifie le délai « sous 48 h »).
  • Deux temps, avec expiration : POST /air/order_cancellations → un DEVIS en attente (refund_amount, refund_to, expires_at) → confirmer AVANT expires_at ; un devis périmé renvoie order_cancellation_stale → re-deviser. Seul le devis le plus récent est confirmable.
  • Où va l'argent : refund_to = "original_form_of_payment" → sur NOTRE moyen de paiement Duffel (le solde prépayé) — c'est ensuite NOUS qui remboursons le client (retour sur le moyen d'origine, virement RIB ou espèces par l'agent, F10) · refund_to = "airline_credits" → un AVOIR NOMINATIF par passager (credit_code à la confirmation) que l'on TRANSMET au client tel quel — jamais converti en espèces.
  • Le montant exact n'est connu qu'au devis — d'où notre promesse client « on te répond avec le montant exact remboursable », jamais un chiffre avant.

Bagages — ce que Duffel donne VRAIMENT (vérifié 27/08 sur la doc officielle)

Implémenté côté serveur (27/08) : table order_services (le contrat Duffel tel quel : provider_service_id, segment_ref/passenger_ref — la soute PAR SENS et PAR PASSAGER —, quantity, amount_cents TEL QUEL jamais re-margé, maximum_weight_kg NULLABLE) + POST /voyage/orders accepte services[] et augmente le total de amount × quantity (la règle Duffel). Schéma validé Postgres 16 réel (58 objets). Brancher la vraie clé = remplacer l'adaptateur, rien d'autre — la transition base réelle est immédiate.
  • Bagage inclus : chaque offre porte slices[].segments[].passengers[].baggages[] = {type: "carry_on" | "checked", quantity} — par passager et par segment, selon la compagnie et le tarif. Aucun poids n'est publié à ce niveau : Duffel dit le NOMBRE de bagages inclus, pas les kilos. À l'écran : « Bagage cabine inclus · selon l'offre de la compagnie ».
  • Bagage soute en plus : available_services de type baggage, récupérés en ajoutant return_available_services=true à la lecture de l'offre. Champs : total_amount/total_currency (le prix de LA compagnie), maximum_quantity, segment_ids + passenger_ids (un service est attaché à des segments et passagers précis → l'option soute se choisit par sens en aller-retour), et metadata — le poids max (souvent 23 kg) n'y figure que si la compagnie le publie ; sinon on affiche « selon la compagnie », jamais un chiffre inventé.
  • Quand : les services s'ajoutent à la création de l'order (champ services: [{id, quantity}]) et le paiement doit être augmenté d'autant — le bagage choisi au tunnel entre donc dans le total à remettre en espèces AVANT le prix bloqué. Des bagages post-réservation existent aussi chez Duffel (guide « Adding Post Booking Bags ») — hors périmètre pilote.
