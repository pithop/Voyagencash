Projet PayEnCash — AJEK SASU Version 2.0 Juin 2026

Introduction

Ce document décrit les contrats d'interface du système, répartis en deux familles. D'abord les deux fournisseurs externes : Duffel (vols, débit du solde prépayé en temps réel) et Hotelbeds APItude (hébergements, modèle post-payé — la réservation est confirmée puis la dette réglée). Ensuite l'API interne PayEnCash qui remplace l'ancien prestataire de paiement : l'encaissement du cash est désormais réalisé par un agent au domicile du client, avec un code-barres généré en interne, un dispatch agent, un suivi temps réel, une validation par code de sécurité + photo, et une notation. Pour chaque API : les endpoints, les payloads de requête et de réponse, et les codes d'erreur à gérer explicitement.

🔄
Changement de modèle (v2.0) L'ancien prestataire externe de paiement en espèces (code-barres scanné dans un point de vente tiers, confirmation par webhook) a été entièrement retiré. PayEnCash génère son propre code, dispatche un agent salarié d'AJEK SASU qui collecte le cash à domicile, et c'est la validation de la collecte par l'agent (code de sécurité + photo) qui déclenche le paiement des fournisseurs — en lieu et place du webhook. Conformité : AJEK SASU est a priori non assujettie LCB-FT (à confirmer par avis juridique) ; le dispositif repose sur un KYC client gradué (renforcé à 3 achats OU 1 000 € sur 7 jours glissants, prestataire PVID), un KYB fournisseurs, le plafond espèces de 1 000 €/transaction avec anti-fractionnement, et un logiciel de caisse sécurisé (CGI 286-I-3° bis).
⚠️
Avant de commencer Les exemples des fournisseurs externes (Duffel, Hotelbeds) sont à valider contre leur documentation officielle au moment de l'implémentation — les API évoluent. Ce document fixe le contrat fonctionnel attendu côté PayEnCash, pas une copie figée d'une référence externe.

✈️ Duffel

Base URL : https://api.duffel.com. Authentification par header Authorization: Bearer duffel_live_xxx (ou duffel_test_xxx en sandbox). Toutes les requêtes nécessitent l'en-tête Duffel-Version: v2.

Contraintes techniques transversales — à respecter sur tous les appels Duffel

ContrainteValeur exactePourquoi c'est critique

Un timeout plus court côté PayEnCash provoquerait une erreur applicative alors que la réservation a peut-être réussi côté Duffel — risque de double traitement ou de perte de suivi d'une commande réellement payée.

Le header ratelimit-reset indique quand la limite sera réinitialisée — à utiliser pour temporiser les retries plutôt que de réessayer immédiatement.
Header de suivi du quotaratelimit-remainingIndique le nombre de requêtes encore autorisées dans la période en cours — permet d'anticiper la limite avant de la heurter, plutôt que de réagir après coup.

Format structuré des erreurs Duffel

Chaque erreur retournée par l'API Duffel suit une structure fixe à deux niveaux : un type (catégorie générale) et un code (raison précise, propre à ce type). Le code HTTP seul ne suffit jamais à distinguer la cause exacte — le couple type + code doit systématiquement être lu et journalisé.

{
  "errors": [{
    "type": "rate_limit_error",
    "code": "rate_limit_exceeded",
    "message": "Too many requests hit the API too quickly. Please retry your request after the time specified in the ratelimit-reset header."
  }]
}

Distinction importante pour le monitoring Un code 502/504 sur airline_error ne veut pas dire que Duffel est en panne — c'est la compagnie aérienne elle-même qui ne répond pas. Le comportement attendu côté PayEnCash diffère : pour une erreur Duffel généralisée, alerter l'équipe technique ; pour un airline_error isolé sur une commande, le traiter comme un échec ponctuel de cette réservation précise (voir Doc 1, cas d'erreur) sans déclencher d'alerte sur l'ensemble du système.

🔴
CRITIQUE — Filtrer les offres incompatibles avec le délai d'encaissement agent Duffel retourne pour chaque offre un objet payment_requirements contenant :
  • requires_instant_payment (boolean) — Si true, l'offre exige un paiement immédiat. INCOMPATIBLE avec PayEnCash car le paiement fournisseur n'intervient qu'après la collecte du cash par l'agent (délai de dispatch + trajet + encaissement). Ces offres doivent être exclues du comparateur.
  • price_guarantee_expires_at (datetime) — Date jusqu'à laquelle le prix est garanti. Si cette date est inférieure à la fenêtre de collecte (orders.collection_deadline_at, Doc 2), le prix peut changer avant le règlement → risque de perte pour PayEnCash. Afficher un avertissement ou filtrer.
  • payment_required_by (datetime) — Deadline absolue. Le règlement Duffel déclenché à la validation agent doit intervenir AVANT.
Le filtrage requires_instant_payment = false est aussi critique que le filtrage paymentType = AT_WEB côté Hotelbeds.
ℹ️
Aller simple vs aller-retour Le nombre de slices dans l'offer_request dépend de orders.trip_type : 1 slice pour one_way, 2 slices pour round_trip (le 2ème slice inverse origin/destination et utilise orders.return_date). Le total_amount retourné par Duffel inclut le prix combiné aller+retour — il n'y a pas de prix séparé par slice. orders.origin_iata est choisi par le client (pas auto-détecté) et orders.cabin_class est envoyé dans le payload.
🔴
Filtrer requires_instant_payment = true Certaines offres Duffel exigent un paiement instantané (payment_requirements.requires_instant_payment = true). Ces offres sont incompatibles avec le flux PayEnCash car le client paie en espèces à l'agent lors de la collecte à domicile, et le règlement fournisseur n'est déclenché qu'à la validation de cette collecte. Le comparateur doit exclure ces offres et ne montrer que celles avec requires_instant_payment = false. De plus, vérifier que payment_required_by laisse suffisamment de temps pour couvrir la fenêtre de collecte (dispatch + trajet agent + encaissement) puis la Phase 5.
⚠️
Problème de timing : born_on pas encore disponible en Phase 1 Duffel recommande de fournir les dates de naissance des passagers dès l'offer_request pour éviter une incohérence tarifaire enfant/adulte entre la recherche et l'achat. Mais en Phase 1, le client n'a pas encore saisi ses informations voyageurs (Phase 2). Stratégie retenue : (1) En Phase 1, utiliser uniquement type: "adult" ou age si le client a déjà précisé le nombre d'adultes et d'enfants via un sélecteur à l'étape initiale, (2) En Phase 5 (POST /air/orders), fournir les born_on complets depuis order_travelers.born_on_enc. Un écart tarifaire résiduel est couvert par la marge de sécurité (Doc 4).

🛵 PayEnCash — Encaissement & encaissement à domicile

Cette API est interne : elle remplace intégralement l'ancien prestataire externe de paiement en espèces. PayEnCash génère son propre code, dispatche un agent salarié d'AJEK SASU (salaire fixe, la tournée ne porte aucun gain — D11 rév.) qui collecte le cash au domicile du client, suit la tournée en temps réel, valide l'encaissement par code de sécurité + photo — ce qui déclenche le règlement des fournisseurs — puis recueille une notation. Tous les endpoints ci-dessous sont exposés sous le préfixe global /api et protégés par l'authentification PayEnCash (JWT client, JWT agent, ou rôle manager selon le cas).

🔐
Trois profils d'appelant Les endpoints sont segmentés par acteur : client (suivi de sa encaissement, notation), agent (ses tournées, position, validation d'encaissement), manager (validation des inscriptions agent, zones, limites, dispatch). Un guard de rôle est appliqué globalement — un agent ne peut pas lire les tournées d'un autre, un client ne voit que ses propres commandes.

1. Génération du code interne (code-barres)

POST/orders/{orderId}/payment-code

Appelé en Phase 3 (Doc 1) quand la commande passe en AWAITING_COURIER. Génère en interne le code-barres et le code de sécurité, crée la ligne payments (Doc 2) et ouvre la fenêtre de collecte. Idempotent : un second appel sur la même commande renvoie le code existant, jamais un nouveau.

Réponse

{
  "paymentId": "pay_01H...",
  "barcodeValue": "PEC-4F9A-20K7-C3",       // → payments.barcode_value (UNIQUE, généré en interne)
  "amountCents": 3700,                       // TTC → payments.amount_cents = orders.total_price_cents
  "vatRate": 0.20,                          // → orders.vat_rate (config manager, défaut 20%)
  "vatAmountCents": 617,                    // → orders.vat_amount_cents — affiché « dont TVA »
  "securityCode": "4821",                    // affiché au client UNE fois — stocké haché (security_code_hash)
  "collectionDeadlineAt": "2026-06-19T18:30:00Z"  // → orders.collection_deadline_at (fenêtre de collecte)
}
🧾
Montant TTC + TVA amountCents est le montant TTC (= orders.total_price_cents). vatAmountCents et vatRate permettent d'afficher « dont TVA » et d'émettre le reçu / la facture (HT + TVA + TTC). Le taux est figé à la génération du code (config manager, défaut 20%).
🔴
Le code de sécurité ne transite qu'une fois Il est affiché au client au moment de la génération et n'est jamais renvoyé par une lecture ultérieure : seul son hash est stocké (payments.security_code_hash). Le client le communique à l'agent lors de la collecte ; l'agent le saisit pour valider (voir §4). Ne jamais le journaliser en clair.
🔵
Deux codes, deux rôles — l'un ne remplace pas l'autre Le code interne (payments.internal_code, ex. PEC-Z6DNX8HV) est affiché au client en code-barres et scanné par l'agent : il identifie la commande. Il est visible par quiconque regarde l'écran, donc il ne prouve rien d'autre. Le code de sécurité (4 chiffres, révélé au client seulement à l'arrivée de l'agent) authentifie la remise : il atteste que le client est présent et consent. La validation de collecte exige les deux. Un scan seul ne doit jamais suffire à encaisser.

4. Validation d'encaissement (déclencheur du paiement fournisseur)

POST/deliveries/{deliveryId}/collect

C'est le cœur du nouveau modèle : l'appel effectué par l'agent après avoir reçu le cash. Il remplace l'ancien webhook de paiement comme unique déclencheur de la Phase 5 (règlement Duffel + Hotelbeds). L'agent scanne le code-barres affiché par le client, saisit le code de sécurité que celui-ci lui dicte, et joint une photo de preuve.

Requête (multipart)

{
  "scannedCode": "PEC-Z6DNX8HV",   // code-barres scanné sur l'écran du client → comparé à payments.internal_code
  "securityCode": "4821",          // comparé au hash payments.security_code_hash
  "collectedAmountCents": 3700,   // montant TTC réellement encaissé → payments.collected_amount_cents
  "proofPhoto": "<fichier binaire>" // → payments.proof_photo_url (bucket chiffré, rétention bornée — D10)
}

Traitement serveur (transactionnel)

  1. Vérifier que scannedCode correspond bien au code interne de cette encaissement — sinon 422 : l'agent est devant la mauvaise commande, rien n'est encaissé.
  2. Vérifier le code de sécurité (hash) et que le montant encaissé correspond — sinon 422, la collecte n'est pas validée.
  3. Exiger la photo de preuve — un appel sans photo est rejeté (422).
  4. Passer payments.status = collected, deliveries.status = CASH_COLLECTED, orders.status = CASH_COLLECTED puis PAID.
  5. Enfiler la Phase 5 dans BullMQ (règlement fournisseurs) — jamais en synchrone dans la requête.
  6. Retourner 200 OK.
🔴
Idempotence sur deliveries.id La validation de collecte doit être strictement idempotente : un rejeu (double tap réseau de l'agent) ne doit jamais déclencher deux fois le paiement fournisseur ni deux transitions d'état. La clé d'idempotence est deliveries.id (une collecte = un encaissement). Toute la logique lourde (Duffel/Hotelbeds) reste en file asynchrone après le 200 OK.

Le tunnel est une commande construite par étapes côté serveur, et non un panier tenu par le navigateur : chaque choix est persisté, ce qui permet de reprendre un parcours interrompu et de figer les prix (Doc 4).
