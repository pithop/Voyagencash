Introduction

Ce document fait le pont entre l'itération de design haute-fidélité v2 (validée pour 6 écrans) et le backend documenté (Doc 1 à 10) d'AJEK SASU (« PayEnCash » désigne l'application). Il fixe, pour chaque écran, son rôle, ses états et son mapping données (table / colonne / endpoint réels).

💡
Écrans voyage uniquement — ligne MODE à part Les 11 écrans ci-dessous couvrent la ligne voyage (vols Duffel / hôtels Hotelbeds). Les écrans de la ligne MODE (catalogue d'articles, panier, expédition, droit de rétractation) ne sont pas construits ici : ils sont spécifiés dans Étape 4 · flux F11/F12 — s'y reporter, ne pas les inventer.

L'espace agent (5ᵉ surface, courier/) a ses propres maquettes dans ui/agent/ — 13 écrans, même charte que l'app cliente, mobile-first strict. Deux d'entre eux portent le circuit du cash : scan du code-barres à la collecte, et dépôt au réseau Cash Services (carte de dépôt nominative) avec déclaration du reçu, dès que l'encours dépasse le seuil de 400 € (paramétrable). Une tournée y est explicitement présentée comme « encaisser puis déposer » : tant que les espèces ne sont pas déposées, l'agent salarié est retiré du dispatch.

La source de vérité visuelle est l'application réelle payencash/frontend/ (composants React + src/styles/theme.css), complétée par DESIGN_SYSTEM.md (charte stricte, à la racine de la documentation). Les maquettes HTML de ui/parcours/ et ui/ecrans/ reprennent cette charte via le kit partagé ui/assets/payencash-v2.css : ils illustrent l'intention et les parcours, mais l'implémentation se lit dans l'app. (Les anciens dossiers de handoff design ont été supprimés : leurs prompts de génération étaient caducs depuis que l'app existe, et leurs visuels étaient corrompus.)

⚠️
Cible = l'app web existante, pas une app mobile native Les écrans sont présentés dans un cadre téléphone (« PhoneFrame »), mais l'implémentation se fait dans l'app cliente web payencash/frontend/ (Next.js, PWA mobile-first). Les noms de champs ci-dessous sont les noms réels du backend (modèle d'encaissement à domicile : le code est généré en interne — payments.barcode_value — et il n'y a plus de prestataire de paiement externe).
✅
Refonte v2 (encaissement à domicile) Les écrans du tunnel (A1→A5) restent inchangés ; le tunnel de paiement est recâblé sur le modèle agent : code interne → attribution agent → suivi live (carte position + ETA) → collecte (code de sécurité + photo, côté espace agent) → notation. Composants partagés : DarkBanner, Countdown (fenêtre de collecte), Segmented, CodeStateView, OrderTimeline, BottomSheet, Splash, BudgetSearchForm, BudgetBar, FilterPill, FlightCard, StayCard, DelaySelector, BoardingPass, CourierLiveMap (ex-RelayMap), CourierTrackingView, RatingStars. L'espace agent est une surface distincte (voir §Écrans à concevoir). Voir « Décisions & écarts » pour les choix arbitrés.

Conventions & charte

La charte stricte est définie dans DESIGN_SYSTEM.md. Rappels structurants applicables à tous les écrans :

  • Profondeur sans bordures : fond + ombre douce, jamais de border (sauf séparateurs internes #F1F4F2 et pointillés du billet).
  • Palette verrouillée : verts/encre/neutres. Pas de bleu, orange réservé à l'urgence (compte à rebours, « ferme bientôt »), rouge réservé à la suppression.
  • Carte live en charte : markers custom (agent en mouvement #10A06A, domicile client #0F2A24, position live agent #0C7F54) — jamais le style SDK par défaut (voir Doc 5, « Carte live d'encaissement »).
  • Typo : Hanken Grotesk (UI) + JetBrains Mono (codes, compte à rebours). Zéro emoji. Icônes Lucide.
  • Compte à rebours : lit toujours la fin de la fenêtre de collecte (orders.collection_deadline_at), jamais un timer codé en dur.

Tunnel de réservation (A1 → A5)

Principe « budget-first ». Le parcours part du budget — pas d'une destination ni de dates figées : l'utilisateur pose ce qu'il veut dépenser, l'app propose des voyages dedans. Cinq écrans mènent du budget à la création de la commande (orders.status = DRAFT en sortie de A5), avant le tunnel de paiement (Code → Billet).

ℹ️
Contrats de navigation Vol : /vols?order=…&origin=…&destination=…&date=…&trip_type=…&cabin_class=economy[&return_date=…]. Séjour : /sejour?order=…&destination=…&check_in=…&mode=stay_only. La cible de retour du tunnel est /budget (même formulaire que l'accueil).

Rôle. Entrée du tunnel. Saisie du budget (curseur + montant), de l'aéroport de départ et de la destination (ou « type de voyage » : vol aller-retour ou séjour seul), puis lancement de la recherche. CTA « Voir les voyages ».

États

  • Formulaire : BudgetSearchForm partagé entre / (accueil) et /budget (retour du tunnel) — une seule source, pas de duplication.
  • Reprise : si une recherche était en cours (pec_budget_pending), pré-remplissage à la réouverture.
  • Splash : écran d'accueil animé au tout premier lancement (pec_splash_seen en localStorage), puis masqué.

États transverses (non maquettés)

Les états vide / chargement / erreur ne sont pas détaillés écran par écran. Les implémenter en appliquant le design system, de façon sobre :

  • Chargement : skeletons neutres (fond #F4F7F5, pas de spinner tape-à-l'œil).
  • Vide : message court + icône Lucide encre + CTA contextuel (ex. « Lance une recherche »).
  • Erreur : encart sobre, action « Réessayer » ; pas de rouge (réservé à la suppression) sauf erreur destructive.

B7 — Suivi : états d'échec et de remboursement

Maquette : ui/ecrans/11-suivi-etats-echec.html. Ce n'est pas une seconde UI d'encaissement — c'est la route /suivi/[orderId] (B2) dans ses états non nominaux, servie par le même composant CourierTrackingView piloté par orders.status. Jusqu'ici l'écran ne rendait que les six statuts du chemin heureux : un client dont la collecte échouait, dont la fenêtre expirait, ou dont l'argent revenait par agent n'avait aucun écran.

💡
« Où est mon argent » est la seule question d'un état d'échec Le bandeau de montant est donc constant d'un état à l'autre, à la même place : seule sa nature change. Neutre quand rien n'a été collecté, encre quand la somme est chez nous, menthe quand elle repart vers le client — le vert restant ce qu'il est dans toute l'app, des espèces. Le fil d'avancement garde lui aussi les mêmes étapes ; seul l'endroit où il casse change.

Ni rouge, ni croix La charte réserve le rouge à la suppression (« Supprimer mon compte »). Un échec de collecte n'est pas une destruction, et un écran rouge ferait paniquer sur un incident dont on garantit l'issue. L'étape non aboutie suit la règle du design system — pastille grise + tiret, jamais une croix rouge. L'ambre reste réservé au seul cas où une horloge tourne et où le client peut encore agir.
🔴
DÉCISION REQUISE : comment prouve-t-on la remise d'une tournée de retour ? La collecte a son appareil de preuve — code de sécurité vérifié + photo (D10). Le retour n'en a aucun : rien, dans le Doc 1, le Doc 3 ni le Doc 7, ne décrit comment on établit que l'agent a effectivement remis les espèces au client. Point à trancher (voir NOUVELLES-FONCTIONNALITES-2026-08.md). La preuve doit d'ailleurs aller dans l'autre sens : c'est le client qui reçoit, donc c'est lui qui devrait attester. Tant que ce point n'est pas tranché, la maquette n'affiche aucun code de sécurité en état CANCELLED — plutôt que d'inventer une mécanique qui contredirait la décision réelle.
