Introduction

Ce document couvre deux volets complémentaires du compte client d'AJEK SASU (« PayEnCash » désigne l'application) : le cycle de vie complet du compte (inscription par OTP SMS, reconnexion, vérification d'identité KYC graduée, espace personnel, suivi d'encaissement, notation, alertes de prix), et le détail A à Z du flux de paiement cash collecté par agent salarié selon les 3 cas produit de la ligne voyage — vol seul, hébergement seul, ou les deux combinés. Il documente également les filtres avancés du comparateur identifiés par audit concurrentiel (Skyscanner, Kayak, Hopper).

💡
Ligne MODE : voir la note dédiée Ce document ne traite que la ligne voyage (billets Duffel / hôtels Hotelbeds). La ligne MODE (articles physiques : point d'entrée catalogue, panier, expédition, droit de rétractation légal) est spécifiée à part dans Étape 4 · flux F11/F12 — s'y reporter pour le parcours d'achat d'articles et ses documents.
💡
Tables concernées (Doc 2) users, otp_codes, user_sessions, price_alerts, orders, flight_offers, stay_offers, payments, supplier_bookings, deliveries, delivery_tracking_events, courier_ratings, notifications. Les quatre dernières manquaient à cette liste alors que ce document décrit le suivi d'encaissement, la notation de l'agent et les notifications.

Vérification d'identité — KYC gradué

AJEK opère un contrôle d'identité gradué par volume, à finalité unique de prévention de la fraude et de sécurité des agents — aucun usage commercial ni profilage. La vérification est opérée par un prestataire certifié PVID (référentiel ANSSI) ; seul le résultat est conservé, jamais les copies de pièces. Le positionnement (AJEK non assujettie LCB-FT, vérification = intérêt légitime à prévenir la fraude) est à confirmer par avis juridique.

PalierDéclenchementEffet côté client
Vérification simpleSystématique dès la 1re commande, avant l'attribution d'un agentLe payeur et le bénéficiaire doivent être la même personne
Vérification renforcéeDès qu'un client dépasse 3 achats OU 1 000 € cumulés sur 7 jours glissants (seuil calculé en continu, sans intervention humaine)Contrôle PVID renforcé requis avant de poursuivre la commande
⚠️
Plafond de paiement en espèces : 1 000 € par transaction Conformément aux art. L112-6 / D112-3 CMF pour les résidents fiscaux français, aucune transaction en espèces ne peut dépasser 1 000 € (paramétrable), avec anti-fractionnement. Ce plafond est contrôlé côté serveur et figé sur la commande à la génération du code — l'app ne peut pas le contourner. Le palier KYC atteint est affiché sur la fiche client du CRM manager (Doc 9).

Alertes de prix

Fonctionnalité identifiée comme différenciante chez Skyscanner (alertes email/push), Kayak (alertes avec prédicteur), Hopper (notifications "c'est le bon moment d'acheter"). Le client configure une alerte sur une route/seuil de budget et reçoit une notification push (via users.push_token) quand un prix descend sous son seuil.

Flux de création d'une alerte

1
Client crée une alerte depuis le comparateur ou l'espace personnel Il sélectionne une route (MRS → BCN), éventuellement une date, et saisit son budget plafond (ex. 20€ tout compris). PayEnCash INSERT dans price_alerts avec budget_ceiling_cents = 2000, is_active = true, expires_at = now() + 30 days.
2
Job CRON horaire (Doc 5) Pour chaque alerte active non expirée, appeler POST /air/offer_requests + GET /air/offers?sort=total_amount&limit=1 pour obtenir le prix le plus bas actuel sur la route. Calculer le prix TTC avec marge fixe.
3
Comparer avec le seuil et le dernier prix constaté Si prix_ttc ≤ budget_ceiling_cents ET prix_ttc < last_checked_price_cents (le prix a vraiment baissé, pas juste atteint le seuil une seconde fois) → envoyer une notification push via FCM.
4
Mettre à jour price_alerts Incrémenter triggered_count. Si triggered_count ≥ 3, passer is_active = false pour éviter le spam. Toujours mettre à jour last_checked_price_cents et last_checked_at.
🔴
Coût API des alertes Chaque alerte active génère un appel Duffel toutes les heures. À 100 alertes actives = 2 400 appels API/jour. Surveiller les quotas Duffel et prévoir une logique de regroupement par route (une seule requête pour toutes les alertes MRS→BCN actives).

Flux de paiement cash A à Z — les 3 cas produit

C'est ici que se jouent les différences concrètes entre les trois usages du produit. Le flux de collecte est identique dans les trois cas — c'est ce qui se passe après la validation de la collecte par l'agent qui diverge : 1 appel API fournisseur (Duffel seul ou Hotelbeds seul) vs 2 appels consécutifs (Duffel puis Hotelbeds).

💡
Point commun aux 3 cas : un seul code interne Quel que soit le cas, le client reçoit toujours un seul code interne, présenté à l'agent lors de la collecte. Ce code correspond à orders.total_price_cents (TTC) — le total peut inclure vol seul, hébergement seul, ou les deux. L'agent encaisse simplement le montant total en espèces, dans la limite du plafond de 1 000 € par transaction (contrôle serveur, voir section KYC).
💡
Proforma avant paiement, reçu numéroté après collecte Avant la génération du code, le client visualise un récapitulatif proforma (montant TTC détaillé, dont TVA) — document non fiscal, sans valeur d'encaissement. Après validation de la collecte par l'agent, la commande CONFIRMED donne lieu à un reçu numéroté (numérotation séquentielle continue, exigence du logiciel de caisse art. 286-I-3° bis CGI) accessible dans « Mes factures ». Le code interne n'est ni le proforma ni le reçu : c'est un identifiant d'encaissement à usage unique.
