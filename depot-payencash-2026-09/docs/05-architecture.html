Architecture technique

Projet PayEnCash Version 1.0 Juin 2026

Introduction

Ce document décrit la stack recommandée, l'architecture globale du système, la stratégie de traitement asynchrone (indispensable pour découpler la validation de la collecte agent des appels fournisseurs Duffel/Hotelbeds, Doc 3), le canal temps réel du suivi d'encaissement, le service de dispatch, l'espace agent et le nouveau bounded-context « encaissement », les environnements, et la politique de sécurité et de conformité RGPD pour les données sensibles (voyageurs, géolocalisation, photos de preuve) définies au Doc 2.

Stack technique recommandée

Backend

Node.js + TypeScript

Écosystème mature pour les intégrations API multiples (Duffel, Hotelbeds) et pour le temps réel (WebSocket/SSE) du suivi d'encaissement. TypeScript apporte la sécurité de typage indispensable sur les calculs de prix (Doc 4) où une erreur de type peut coûter de l'argent réel.

Base de données

PostgreSQL 16+

Imposé par le schéma du Doc 2 (JSONB, UUID, extension PostGIS pour les zones d'encaissement et le suivi de position agent, contraintes CHECK avancées).

File d'attente

BullMQ (sur Redis)

Nécessaire pour découpler la validation de la collecte agent (qui doit répondre vite, Doc 3) des appels Duffel/Hotelbeds et du dispatch (qui peuvent prendre plusieurs secondes). Retry automatique intégré avec backoff exponentiel.

Frontend

React + Vite (ou Next.js)

Cohérent avec les prototypes HTML déjà construits (tunnel de vente) — composants réutilisables pour le slider budget, le stepper voyageurs, la bascule jour/nuit.

Chiffrement

Chiffrement applicatif AES-256-GCM

Pour les colonnes *_enc de order_travelers (Doc 2) — voir section Chiffrement plus bas pour le choix précis et sa justification.

Hébergement

Auto-hébergé — OVH + CapRover

Déploiement sur serveur OVH (données en France/UE, conformité RGPD simplifiée) via CapRover (PaaS auto-hébergé : build, déploiement, TLS, scaling des conteneurs). Cohérent avec l'architecture de déploiement existante de PayEnCash.

Temps réel

WebSocket ou SSE

Canal temps réel pour la carte live d'encaissement (position agent + ETA) côté client, et les notifications de tournée côté espace agent (nouvelle tournée, réassignation), style VTC (Doc 1, Doc 3). Alimenté par les heartbeats de position POST /deliveries/{id}/location.

Notifications push

Firebase Cloud Messaging (FCM)

Standard de facto pour les notifications push cross-platform. Nécessite un compte Firebase et l'intégration du SDK dans l'app. Le token FCM par appareil est stocké dans users.push_token (Doc 2) et mis à jour à chaque ouverture de l'app. Utilisé pour les alertes de prix (Doc 10) et les rappels pré-départ (Doc 7).

SMS OTP (authentification)

Brevo SMS

Prestataire retenu (déjà utilisé pour l'email transactionnel PayEnCash). Service tiers indépendant des fournisseurs voyage. À vérifier au paramétrage : coverage France + Maghreb (segment Royal Air Maroc, Air Algérie, Tunisair, Doc 6) et quotas d'envoi. Utilisé pour le flux OTP du Doc 10.

Carte live d'encaissement (charte)

Le suivi de l'encaissement (écran suivi agent, UI v2 — Doc 11) s'appuie sur une carte live affichant la position de l'agent et l'ETA, alimentée en temps réel par delivery_tracking_events (courier_lat, courier_lng) et les zones delivery_zones (Doc 2 ; extension PostGIS pour le dispatch de proximité). Le rendu doit respecter la charte produit (DESIGN_SYSTEM), jamais le style par défaut du SDK.

ℹ️
Note d'implémentation — carte en charte
  • SDK au choix (MapLibre / Mapbox / Google Maps), mais markers custom obligatoires : agent en mouvement vert (#10A06A), domicile du client encre (#0F2A24), position live de l'agent vert foncé (#0C7F54).
  • Interdiction du style par défaut du SDK (pin bleu/rouge, point bleu de géolocalisation). Aucun bleu/rouge sur la carte ; l'orange est réservé à l'urgence (retard).
  • Affichage temps réel : position de l'agent + ETA, poussés via le canal WS/SSE (heartbeats POST /deliveries/{id}/location, Doc 3).
  • Actions : « Appeler l'agent » et suivi du statut de la tournée (assigné → en route → arrivé → collecté), dérivé de deliveries.status (Doc 2).

Architecture globale

ℹ️
Point clé Il n'y a plus de webhook de prestataire de paiement. C'est la validation de la collecte par l'agent (route POST /deliveries/{id}/collect depuis l'espace agent, Doc 3) qui pousse immédiatement le job de Phase 5 dans la file d'attente, plutôt que de traiter la logique métier en synchrone. Le suivi d'encaissement (position + ETA) transite par un canal temps réel WS/SSE exposé par le même API Gateway.

File d'attente asynchrone

Trois jobs distincts doivent être mis en file après la validation de la collecte agent (Doc 1, Phase 5) :

JobDéclenché parTentatives maxBackoff
book-flightValidation collecte agent32s, 8s, 30s
book-stayValidation collecte agent (parallèle au précédent)32s, 8s, 30s
send-confirmationSuccès des deux jobs précédents55s, 15s, 60s, 300s, 900s

Implémentation (pseudo-code)

// Dans le handler de validation de collecte (POST /deliveries/{id}/collect), après transaction DB réussie (Doc 2)
await flightQueue.add('book-flight', { orderId }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 2000 }
});

if (order.hasAccommodation) {
  await stayQueue.add('book-stay', { orderId }, {
    attempts: 3,
    backoff: { type: 'exponential', delay: 2000 }
  });
}

// Worker séparé, écoute les deux queues
flightQueue.on('completed', async (job) => {
  await checkAndFinalizeOrder(job.data.orderId);
});

async function checkAndFinalizeOrder(orderId) {
  const bookings = await db.supplier_bookings.findByOrderId(orderId);
  const allDone = bookings.every(b => b.status === 'success');
  if (allDone) {
    await db.orders.update(orderId, { status: 'CONFIRMED', confirmed_at: now() });
    await confirmationQueue.add('send-confirmation', { orderId });
  }
}

Authentification de l'espace manager

L'espace manager (Doc 9) est une application web distincte de l'app client, avec son propre système d'authentification basé sur la table manager_users (Doc 2). Elle n'est accessible que par la fondatrice (rôle owner) et, à terme, d'éventuels employés (rôle operator).

DomaineImplémentation recommandée
AuthentificationSession JWT signée côté serveur — email + mot de passe hashé en bcrypt/argon2 (manager_users.password_hash). Pas de OAuth tiers pour ne pas dépendre d'un service externe pour un accès aussi sensible.
Durée de sessionToken d'accès à courte durée (ex. 2h), refresh token en cookie HttpOnly. Pas de "rester connecté" illimité.
Séparation des routesLes routes /manager/* doivent être sur un sous-domaine ou une application serveur distincte — jamais exposées par le même processus que l'app cliente publique. Pas de partage de session entre l'app client et l'espace manager.
Contrôle de rôleVérifier le rôle manager_users.role à chaque requête sensible côté serveur — pas uniquement côté UI. En particulier : modification de margin_config, delivery_fee_config, du taux de TVA (vat_rate) et des zones/limites, ainsi que la validation des inscriptions agent, strictement réservée au rôle owner (Doc 9).
Logs d'accèsToute connexion, déconnexion, et action sensible (modification de marge, annulation manuelle de commande) doit être écrite dans audit_log avec actor = manager_users.display_name.
Accès en dehors des locauxConsidérer un accès restreint par IP ou VPN si l'espace manager est géré depuis un lieu fixe — simple couche supplémentaire au-delà du couple email/mot de passe.

Chiffrement des données voyageurs

Les colonnes given_name_enc, family_name_enc, born_on_enc de la table order_travelers (Doc 2) doivent être chiffrées au repos.

Choix recommandé : chiffrement applicatif AES-256-GCM

Plutôt que pgcrypto (chiffrement côté PostgreSQL), un chiffrement applicatif est recommandé pour garder la clé de chiffrement totalement hors de la base de données — une fuite de la base seule (dump SQL volé) ne suffit alors pas à exposer les données.

const crypto = require('crypto');

function encryptField(plaintext, key) {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();
  // Stocker iv + authTag + encrypted ensemble dans la colonne BYTEA
  return Buffer.concat([iv, authTag, encrypted]);
}

function decryptField(stored, key) {
  const iv = stored.slice(0, 12);
  const authTag = stored.slice(12, 28);
  const encrypted = stored.slice(28);
  const decipher = crypto.createDecipheriv('aes-256-gcm', key, iv);
  decipher.setAuthTag(authTag);
  return Buffer.concat([decipher.update(encrypted), decipher.final()]).toString('utf8');
}
⚠️
Gestion de la clé de chiffrement La clé AES doit elle-même être stockée dans le vault (jamais dans le code), avec idéalement une rotation périodique gérée par un service de gestion de clés (KMS) plutôt qu'une clé statique unique sur toute la durée de vie du projet.

Les données déchiffrées ne doivent exister en mémoire que le temps strictement nécessaire à l'appel API (transmission à Duffel, Phase 5 du Doc 1) — jamais mises en cache, jamais journalisées même temporairement.

  • Clés SDK carto, service de notifications push et bucket de photos (chiffré, rétention bornée) provisionnés
  • Procédure de dépôt du cash par les agents et rapprochement collecté → déposé en place
  • Taux de TVA (vat_rate) configuré et génération de facture HT + TVA + TTC vérifiée (Doc 4 / Doc 10)
  • Test de bout en bout réel : commande complète, cash réel collecté par un agent à domicile, vérification de la réservation effective
  • Jobs CRON activés et vérifiés en environnement de staging avant bascule
  • Politique de confidentialité et mentions légales publiées, validées juridiquement (incl. géolocalisation + photos)
  • Procédure de remboursement par retour cash agent documentée pour l'équipe support
  • Alerting Slack/email opérationnel et testé avant le premier client réel
