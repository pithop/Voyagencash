Guide de démarrage local

AJEK SASU — application PayEnCash Version 1.0 Révisé le 18 septembre 2026

Ce guide donne tout ce qu'il faut pour passer de zéro à un environnement de développement fonctionnel, avant même d'écrire la première ligne de logique métier. Il s'appuie sur la stack recommandée au Doc 5 (Architecture technique) — si une autre stack est choisie, les principes restent valables mais les commandes ci-dessous devront être adaptées.

Prérequis

OutilVersion minimaleUsage
Node.js20 LTSRuntime backend et frontend
npm ou pnpmnpm 10+ / pnpm 9+Gestion des dépendances
PostgreSQL16+Base de données — imposé par le schéma du Doc 2 (JSONB, UUID, extension PostGIS)
Redis7+File d'attente BullMQ (notification du prestataire, paiement fournisseur) et canal temps réel (Doc 5)
Git2.40+Gestion de version
💡

Installation

1. Cloner le dépôt et installer les dépendances

git clone <url-du-depot> payencash
# cd dans le dossier backend
cd payencash/backend
npm install

# cd dans le dossier frontend, dans un second terminal
cd ../frontend
npm install

2. Lancer PostgreSQL et Redis (option Docker)

# Si un docker-compose.yml est fourni à la racine du dépôt
docker compose up -d postgres redis

# Sinon, installation locale classique :
# PostgreSQL : créer une base "payencash_dev"
# Redis : lancer le service par défaut sur le port 6379

3. Configurer les variables d'environnement

Copier le fichier d'exemple et le compléter avec les clés sandbox obtenues (voir section "Comptes à créer" ci-dessous) :

cp .env.example .env

4. Appliquer le schéma de base de données

# Selon l'outil de migration retenu, par exemple avec Prisma :
npx prisma migrate dev

# Ou directement via un script SQL reprenant les 35 tables détaillées au Doc 2
# — complétées par les entités d'août 2026 (KYB/KYC, cash & rémunération, RH,
#   points de collecte, comptabilité de gestion) spécifiées dans
#   MODELE-DONNEES-COMPLEMENT-2026-08.md

5. Lancer les serveurs de développement

# Terminal 1 — backend
cd backend
npm run dev

# Terminal 2 — worker de file d'attente (dispatch agent, tracking, paiement fournisseur)
cd backend
npm run worker

# Terminal 3 — frontend
cd frontend
npm run dev
⚠️
Le worker n'est pas optionnel Sans le processus worker actif, la notification du prestataire ne déclenchera jamais le paiement fournisseur (Duffel / Hotelbeds) — aucune commande ne passera au statut CONFIRMED. Voir Doc 5, section "File d'attente asynchrone", pour la justification de cette séparation.

Depuis le 18/09 au soir, l'agent de caisse mobile est supprimé : plus de terminal d'agent, plus de contrat d'acquéreur TPE, plus de réseau Cash Services, plus de recrutement d'agents. Il reste deux moyens, achetés au comptoir d'un commerce : le Bon d’achat PayEnCash vendu par des commerçants partenaires sous contrat de distribution (titre prépayé émis par AJEK, moyen de paiement à usage limité, art. L521-3 CMF — Étape 3 §2b) : le bon d’achat se règle dans le bus AJEK. UN SEUL PRESTATAIRE, Stripe (1,5 % + 0,25 € par transaction carte EEE, tarif relevé le 18/09 — retenu le 21/09 pour les deux lignes, Mode et PayEnCash Solution) — c'est lui qui prélève le commerçant à chaque vente : la carte enregistrée de son commerce est débitée du montant du bon d’achat moins sa commission (1,10 % HT + TVA 20 %), et aucun bon d’achat n'est créé si la banque refuse. Il n'y a donc plus ni créance, ni échéance, ni relance : il reste un relevé mensuel et l'autofacture de commission (art. 289 CGI). L'authentification forte est faite une fois, à l'enregistrement de la carte (SetupIntent Stripe) ; reste à obtenir de Stripe, par écrit, l'acceptation de l'activité « cartes cadeaux » avant le passage en réel. En contrepartie, il faut mettre en place le KYC client gradué et le KYB fournisseurs (ligne Mode) ainsi que le KYB des commerces partenaires. AJEK SASU n'est a priori pas assujettie LCB-FT — à confirmer par avis juridique avant mise en production.

Tester le Bon d’achat PayEnCash en 5 minutes (maquette, 18/09)

Le troisième moyen de payer sans carte se teste de bout en bout dans la maquette (serveur local python3 serve-8777.py, puis http://localhost:8777/PORTAIL.html). Zéro seed : il n'existe aucun point de démo, tout part d'une inscription.

  1. Inscription du commerce — ui/partenaire/00-inscription.html : enseigne, adresse, SIRET, e-mail (code reçu), puis les pièces du coffre (Kbis, pièce du gérant, vidéo) → « transmis ». Le point naît en contrat_a_signer.
  2. Dossier — Manager 29-partenaires (ou 40-comptes) : valider la candidature et chaque pièce du coffre.
  3. Contrat — le partenaire signe depuis partenaire/07-mon-point, ou le commercial envoie le lien (commercial/03-signature → page gérant commercial/09-signature-gerant, code OTP).
  4. Activation — Manager 29-partenaires → « Activer » (exige dossier valide ET contrat signé) : le point passe actif, il apparaît dans « Où acheter un bon d’achat » (ecrans/25).
  5. Vente — partenaire/03-vendre : montant (5–250 €), case « j'ai encaissé le montant auprès du client », « Émettre le bon d’achat » → prélèvement sur la carte du commerce, puis ticket imprimable avec le code.
  6. Paiement client — fly/01 ou mode/05 : carte « Bon d’achat PayEnCash », code, « Vérifier » (solde), puis « Payer avec mon bon d’achat » (tout) ou « Utiliser X € » (le reste par un autre bon de la série). En fin de mois : Manager 29 → le relevé du point, d'où s'émet l'autofacture de commission.
💡
Ce que le partenaire ne fait jamais — scanner un code de paiement, encaisser une commande, rembourser, rendre la monnaie sur un bon d’achat : le bus refuse payer(..., par:'partenaire'). Le partenaire vend un titre et en reverse le prix ; le remboursement d'une commande réglée par bon d’achat re-crédite le bon d’achat (rembourser(ref, {mode:'bon'})).

Ordre de développement suggéré

Suggestion de séquencement, en cohérence avec les 5 phases du flux métier (Doc 1) :

  • Schéma de base de données complet (Doc 2) avant tout le reste — tout en dépend
  • Intégration Duffel en lecture seule (recherche d'offres, Phase 1) pour valider la connexion API la plus simple
  • Tunnel de vente frontend (écrans 1 à 3, en s’appuyant sur les maquettes ui/parcours/ et ui/ecrans/ — logique API réelle, sessionStorage, scénarios A/B/C — comme référence à jour ; à reconstruire avec de vraies données)
  • Génération du code interne + du code de sécurité (Phase 3) — hachage du code, aucune valeur en clair en base
  • Ouvrir très tôt le contrat — Stripe (enregistrement de la carte des commerces et prélèvement à la vente ; Connect pour les marques de PayEnCash Solution), accès à l'export/rapport de transactions, compte bancaire de l'entreprise. Ce sont des démarches commerciales à délai, pas du développement : les lancer avant le premier commerce partenaire (voir outils-integration/outils-a-integrer.html)
  • KYC client gradué (3 achats ou 1 000 €/7 jours, PVID) et KYB fournisseurs (ligne Mode, voir Étape 4 · flux F11/F12) — à cadrer avant l'ouverture au public
  • Domaine réseau partenaire : chaîne d'ouverture d'un point, ordonnée : inscription du commerce → dossier KYB au coffre (Kbis, pièce du gérant, vidéo) validé pièce par pièce → contrat de distribution signé (lien jetonné + code OTP au gérant) → carte du commerce enregistrée → activation par le manager. Chaque porte est bloquante : sans dossier valide, pas de contrat ; sans contrat, pas d'activation ; sans carte valide, pas de vente — c'est elle qui règle PayEnCash à chaque bon d’achat émis.
  • Les moyens de règlement (17/09, révisé le 18/09 au soir — le canal agent est supprimé) : orders.channel (psp | soldee) et orders.pay_method (bon, et lui seul depuis le 20/09) ; POST /encaissement/payments/:ref/psp-intent ouvre la transaction (psp_transactions) et POST /encaissement/psp/pingback la règle — seule la notification serveur règle une commande, jamais le retour du navigateur. Plus de dispatch par distance, plus de frais de déplacement.
  • Le service bons d’achat (18/09) : POST /partners/:id/bons (émettre, journal), GET /bons/:code (état + solde, sans PII), POST /payments/:ref/bon (appliquer ou débiter selon le reste dû, transaction SQL), POST /bons/:code/recredit (manager), POST /bons/:code/bloquer, POST /partners/:id/cards/setup puis /cards (enregistrer la carte du commerce chez Stripe, en deux temps), GET /partners/:id/releves/:mois, POST /partners/:id/releves/:mois/autofacture — tables partners, partner_cards, partner_charges, gift_cards (étendue : origine, partenaire, solde, ticket), gift_card_movements, signature_links, vue v_partner_monthly_statements ; librairie pure lib/bons.js (code, montant, état, débit possible, relevé au centime). L'émission est transactionnelle : le prélèvement d'abord, le bon d’achat ensuite — une carte refusée ne doit laisser aucun code derrière elle, et une écriture refusée doit rembourser le prélèvement. Le bon d’achat ne passe par aucun prestataire tiers.
  • Numérotation séquentielle continue des tickets de bon d’achat (préfixe BV-) et des autofactures de commission — à brancher avant la première vente réelle : un compteur séquentiel ne se reconstitue pas après coup. L'obligation de logiciel de caisse certifié (art. 286-I-3° bis CGI) visait l'encaissement d'espèces par AJEK : à refaire qualifier par le comptable maintenant qu'AJEK n'encaisse plus au comptoir.
  • Règlement d'une commande (notification du prestataire, ou débit d'un bon d’achat) + file d'attente (Phase 4) — point critique, à ne pas développer en dernier sous pression de délai : c'est l'évènement qui déclenche le paiement fournisseur
  • Intégration Duffel en écriture (achat réel) et Hotelbeds (Phase 5, post-payé : confirmation puis règlement immédiat)
  • Logique d'annulation et de remboursement (Doc 7). Le montant est tranché : il est borné par ce qu'AJEK récupère du fournisseur (D2 rév.) et peut être nul sur un tarif non remboursable. ✅ Le canal est tranché (2026-08-03, révisé au pivot du 17/09) — cancellation_requests.refund_method ∈ bon (le montant re-crédite le bon d’achat — jamais d'espèces, jamais de rendu de monnaie) · virement · avoir_compagnie. La « remise au point d'encaissement » et la course de retour au domicile n'existent plus. Le cas d'échec fournisseur après collecte (D4) suit la même contrainte : la commande est mise en attente de résolution puis retentée, mais ce qui est rendu reste borné par la récupération
  • Questionnaire de satisfaction (1-5★) et agrégation de la note moyenne, côté hotline
  • Catalogue des emails transactionnels et rappel avant expiration (Doc 7)
  • Segment Maghreb (Doc 6) une fois le flux généraliste stable
